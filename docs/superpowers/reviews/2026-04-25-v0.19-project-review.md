## 1. Verdict

The project is in good shape for a **single-host KVM lab/dev tool**. v0.19 multi-VM concurrency is the right next step. Code is small (≈4 100 lines), tested (445 tests / 95 % cov), ruff-clean, and the spec/plan documents are unusually disciplined.

The honest delta to "trusted in RHEL 9 production" is **not in correctness** — most paths are fine — it's in **operational features** (steady-state probes, scheduling, Prometheus metrics, crash-recovery), and a small number of latent bugs that v0.19's parallelism made reachable.

Triage at the bottom (§7).

## 2. Latent bugs (verified by reading source)

### HIGH

| # | Where | Bug | Why it matters |
|---|---|---|---|
| H1 | `runrecord.py:163-172` | Run-record filenames use **second-granularity** timestamps: `f"{compact}-{fault_slug}-{vm}.json"` where `compact = "%Y%m%dT%H%M%SZ"`. Two parallel-batch steps with the same fault on the same VM started in the same second produce **identical filenames**. `os.replace()` silently overwrites the first record. | v0.19's parallel-batch feature makes this hit-able; before v0.19 it was theoretical. **Confirmed in today's lab run:** Run 2 of the v0.19 parallel-batch validation (`/tmp/test-parallel.toml`, two `vm.pause`/`server1` steps) produced exactly **one** file on disk — `~/.local/state/kvmchaos/runs/20260425T101011Z-vm-pause-server1.json` — containing one set of 3 steps, not two. The second worker's record silently overwrote the first. **Audit-trail integrity broken under fan-out / parallel batches.** Fix: append `%f` (microseconds) or a short random suffix; or write `<basename>-<vm-index>.json` for fan-out. |
| H2 | `cli.py:1124-1129` | `KeyboardInterrupt` during a parallel hold is delivered to the main thread only; sibling worker threads keep sleeping until `step.duration` elapses. The code itself acknowledges the gap in a comment. | Ctrl-C means "stop the chaos *now*" to an operator. Sibling VMs remain in the fault state for up to `duration` seconds. Fix: shared `threading.Event` set on first KeyboardInterrupt; workers poll it inside the sleep loop. Same Event also lets `_run_step` short-circuit before calling `revert`. |
| H3 | `faults/disk_fill.py:62-90` (inject) + runner | `subprocess.run(["fallocate", ...], check=True)` can leave a partially-allocated file behind on ENOSPC mid-call. Inject raises → the runner in `cli.py:_run_experiment_step_on_vm` returns a `_StepOutcome(success=False)` **without calling `revert()`** (revert is only invoked on verify-fail or after a successful hold). The fill file persists across runs. | Recurring inject-fail with a half-allocated file = silent disk leak in `<image-dir>/.kvmchaos-fill-<vm>`. Fix: `inject` wraps `subprocess.run` in `try/except` and `unlink(missing_ok=True)` before re-raising; alternatively `_run_step` always invokes `revert` if `inject` raised (matching what `verify`-fail does). |

## 4. Production-readiness gaps (vs industry chaos tools)

Full table is in `docs/superpowers/followups/2026-04-25-prod-chaos-gap-analysis.md`. Top five for production credibility, ranked by leverage:

1. **Steady-state hypothesis / probes during the chaos window** *(everyone except Pumba has this)*. Today a fault that breaks the guest worse than expected runs the full `duration` regardless. A `[[probe]]` block (HTTP / TCP / `exec`) evaluated before run and every N seconds — first failure triggers immediate `revert()`. Chaos Toolkit's `steady-state-hypothesis` is the prior art. **High leverage, fits the agent-less scope, ≈300 LOC.**

2. **Cron / scheduled experiments**. A `kvmchaos schedule add --cron "0 3 * * 6" experiment.toml` writing to `~/.config/kvmchaos/schedule.toml` plus a `kvmchaos schedule run` tick (driven by a systemd timer) is in scope. Chaos Mesh `Schedule` CRD is the model. **Medium leverage, low risk.**

3. **Restricted time windows / safety calendar**. Gremlin "Restricted Testing Times" — a `[safety] forbidden_windows = ["Mon-Fri 09:00-18:00 Europe/Vienna"]` block refused at run-start. ~50 LOC.

4. **Prometheus exporter (reopen v0.16 decision)**. v0.16's design explicitly excluded this; from a production-credibility standpoint it's the single biggest gap, because SREs cannot alert on **stuck reverts** or **run failures** from JSONL files. A minimal `kvmchaos serve --prom-port 9876` exposing run counts, in-flight faults, last-revert-failed gauge would close it. Litmus's chaos-exporter is the prior art.

5. **Crash recovery / orphan-fault detection**. If the `kvmchaos` process dies during a hold, faults like `net.partition` and `disk.latency` persist on the host indefinitely. A `kvmchaos doctor` (or auto-scan on startup) that reads `~/.local/state/kvmchaos/runs/` for in-progress records and offers to revert them would be a durable safety net. **High value for the "test in prod" promise.**

Out of scope (don't add): multi-host orchestrator, web dashboard, RBAC, JVM faults — `PLAN.md` rejects these and they remain correct rejections.

## 5. Missing KVM/libvirt fault types

Three obvious candidates that fit agent-less single-host scope:

1. **`vm.cpu_stress` / `vm.mem_stress`** — every comparator ships these. Agent-less route: `virDomain.setVcpus()` to pin/unpin vCPUs and `virDomain.setMemory()` (balloon-shrink) — fully reversible via libvirt API. Distinct from `vm.starve` (which uses cgroup CPU quotas).
2. **`vm.reset` / `vm.crash`** — distinct from `vm.kill`: simulates a watchdog-triggered reboot. `virDomain.reset(0)` (hard reset) and `virDomain.injectNMI()` for kernel-panic-on-NMI guests. Exercises systemd boot ordering and recovery scripts. Chaos Mesh `PhysicalMachineChaos` does both.
3. **`disk.detach` / `net.detach`** — hot-unplug. `virDomain.detachDeviceFlags(xml, VIR_DOMAIN_AFFECT_LIVE)` against a target disk or NIC; `attachDeviceFlags` on revert. Exercises hot-unplug paths that timeouts can't reach.

## 6. Test gaps (≥85 % line coverage masks these)

The 95 % line coverage is real but doesn't cover the high-risk axes. Verified by reading `tests/`:

1. **No test for parallel fan-out with mid-flight errors.** The existing `test_experiment.py` covers the dataclass + TOML loader; concurrency tests exist but exercise the happy path. There is no test for: 3-VM fan-out where VM 2 fails while VM 1 and VM 3 are still in their hold — does the runner aggregate the failures correctly? Does revert run for the successful workers?
2. **No test for SIGTERM during hold.** `cli.py` installs a SIGTERM handler; no test sends SIGTERM to a running experiment and asserts revert ran.
3. **No filename-collision test** (H1). Easy to add: write two records with identical `started_at` and assert both are persisted.
4. **No idempotency / replay test.** Run the same experiment twice in succession and assert it converges to the same end state.
5. **No fuzz/property test on `config.py`** (298 lines, 5+ TOML sections). Hand-written tests cover the documented shapes; malformed inputs are likely to crash with `KeyError` or `AttributeError` instead of a friendly message.

## 8. Open questions — resolved 2026-04-25

All three answered and recorded in `PLAN.md`'s Decisions Log.

1. **Scope tightened: kvmchaos must run on the hypervisor host.** v0.20.0 removes `qemu+ssh://` support entirely — the half-support since v0.3 was dishonest (`vm.*`/`clock.skew` worked over SSH; `net.*`/`disk.*` rejected it). Phase 6 SSH-based remote `tc`/`cgroup` executor is rejected — agent-less stance preserved.
2. **Prometheus stays out of scope.** Operating model is interactive lab/prod-lab use, not cron/unattended. v0.16's rejection holds. Reopen only if the operating model ever shifts to scheduled/unattended runs (in which case the textfile-collector pattern in §4 is the cheapest path).
3. **`kvmchaos doctor`: report-only default, `--auto-revert` opt-in.** Avoids breaking operator-intended state (manually-paused VMs, etc.). v0.20 implementation per §7 triage.
