# kvmchaos v0.19 — Multi-VM Concurrency Design

**Date:** 2026-04-25
**Status:** Approved

---

## Goal

Extend the experiment runner to inject faults on multiple VMs concurrently. Two orthogonal axes of parallelism:

1. **Fan-out** — a single step targets multiple VMs simultaneously (`vms = ["db1", "db2"]`)
2. **Parallel batches** — consecutive steps marked `parallel = true` execute concurrently (different faults, different VMs)

Both use `ThreadPoolExecutor`. No new runtime dependencies.

---

## Data Model

### `Step` changes (`src/kvmchaos/experiment.py`)

`Step` is currently a `frozen=True` dataclass with `vm: str` as a required field. Add two new optional fields and keep `vm` for backward compatibility:

```python
@dataclass(frozen=True)
class Step:
    fault: str
    vm: str = ""           # legacy single-VM shorthand; mutually exclusive with vms
    vms: tuple[str, ...] = field(default_factory=tuple)
    parallel: bool = False
    duration: int = 20
    # ... existing fields unchanged ...
    continue_on_failure: bool = False

    def __post_init__(self) -> None:
        if self.vm and self.vms:
            raise ValueError("Step: 'vm' and 'vms' are mutually exclusive")
        if not self.vm and not self.vms:
            raise ValueError("Step: one of 'vm' or 'vms' is required")
        if self.vm:
            # Normalize: store everything in vms
            object.__setattr__(self, "vms", (self.vm,))
```

The runner always iterates `step.vms`. `vm` is preserved as the user-facing shorthand; `vms` is the internal canonical form after normalization.

### `load_experiment` changes (`src/kvmchaos/experiment.py`)

The current parser raises `ValueError` when `vm` is missing. Update it to accept either `vm` (string) or `vms` (list of strings), validate mutual exclusivity, and pass both through to `Step`:

```python
if "vm" not in raw and "vms" not in raw:
    raise ValueError(f"experiment {path}: step {i} missing 'vm' or 'vms'")
if "vm" in raw and "vms" in raw:
    raise ValueError(f"experiment {path}: step {i} has both 'vm' and 'vms'")

vm = str(raw.get("vm", ""))
vms = tuple(str(v) for v in raw.get("vms", []))
```

### TOML backward compatibility

All existing experiment files with `vm = "..."` continue to work unchanged. The `[[step]]` TOML key is unchanged (not `[[steps]]` — the existing key is `step`).

#### TOML examples

Fan-out (same fault, multiple VMs concurrently):
```toml
[[step]]
fault = "vm.pause"
vms = ["db1", "db2"]
duration = 10
```

Parallel batch (different faults, different VMs, run simultaneously):
```toml
[[step]]
fault = "net.latency"
vm = "web1"
parallel = true

[[step]]
fault = "disk.latency"
vm = "db1"
parallel = true
```

Mixed (fan-out step in a parallel batch):
```toml
[[step]]
fault = "vm.pause"
vms = ["db1", "db2"]
parallel = true

[[step]]
fault = "net.latency"
vm = "web1"
parallel = true
```

## Runner (`src/kvmchaos/cli.py`)

### Current structure (unchanged)

- `_run_step(func, domain, *, action, fault_name, vm, ...)` — executes one fault action (inject, verify, or revert) on a single domain, returns `dict[str, object]`.
- `_run_experiment_step(step, *, resolved_uri, dry_run, ...)` — opens a libvirt connection, looks up the domain, orchestrates the inject → hold → verify → revert cycle for one step, raises `typer.Exit` on failure.
- Runner loop — iterates `experiment.steps` sequentially, calls `_run_experiment_step`, handles `continue_on_failure`.

### New internal type

Add a lightweight dataclass near the top of the CLI module (internal — not exported):

```python
@dataclass
class _StepOutcome:
    vm: str
    success: bool
    exit_code: int = 0
```

### Fan-out within a step

Rename current `_run_experiment_step` to `_run_experiment_step_on_vm(step, vm_name, *, resolved_uri, dry_run, config_path, force) -> _StepOutcome`. It operates on a single VM (same logic as today, but takes `vm_name` explicitly instead of reading `step.vm`).

New `_run_experiment_step(step, *, resolved_uri, dry_run, config_path, force) -> list[_StepOutcome]` fans out:

```python
def _run_experiment_step(step, *, resolved_uri, dry_run, config_path, force):
    max_workers = min(len(step.vms), 8)
    with ThreadPoolExecutor(max_workers=max_workers) as pool:
        outcomes = list(pool.map(
            lambda vm: _run_experiment_step_on_vm(
                step, vm, resolved_uri=resolved_uri,
                dry_run=dry_run, config_path=config_path, force=force,
            ),
            step.vms,
        ))
    return outcomes  # caller checks for failures
```

### Parallel step batches (runner loop)

Replace the sequential `for i, step in enumerate(experiment.steps):` with a batch-aware loop. Before executing a step, collect the contiguous run of `parallel=True` steps starting at the current index:

```python
def _collect_parallel_batch(steps, start_idx):
    batch = []
    i = start_idx
    while i < len(steps) and steps[i].parallel:
        batch.append((i, steps[i]))
        i += 1
    return batch  # empty list means current step is not parallel
```

If `batch` has ≥ 2 steps, submit all to a `ThreadPoolExecutor` and collect all outcomes before applying `continue_on_failure`. A single `parallel=True` step with no adjacent parallel neighbors executes sequentially (no error, no special case).

### Error handling

Both fan-out and parallel batches use **complete-then-report**: all tasks run to completion before results are evaluated. After collecting `list[_StepOutcome]`, the runner loop:
1. Counts failed outcomes and increments `failed_steps`
2. If any failed and `step.continue_on_failure` is False, raises `typer.Exit(1)` (existing behaviour)
3. If any failed and `step.continue_on_failure` is True, logs and continues (existing behaviour)

The existing `continue_on_failure` is per-step. For a parallel batch, the batch is treated as a unit: if any step in the batch fails and that step has `continue_on_failure=False`, the experiment stops after the batch completes.

## Observability

The existing `inject.start/success/error` and `revert.success/error` events carry a `vm` field — no schema change needed. Fan-out emits one event set per VM (from within `_run_experiment_step_on_vm`).

One new DEBUG event emitted from the runner loop when a parallel batch starts:

```json
{
  "event": "experiment.parallel_batch",
  "level": "DEBUG",
  "step_count": 2,
  "vms": ["web1", "db1"]
}
```

## Testing

All new paths tested at unit level in `tests/test_experiment.py` (model) and `tests/test_cli.py` (runner). No lab validation required — no new libvirt calls.

### `Step` model validation (`tests/test_experiment.py`)
- `vm = "x"` alone → `step.vms == ("x",)`
- `vms = ["a", "b"]` → `step.vms == ("a", "b")`
- `vm` + `vms` both set → `ValueError`
- Neither `vm` nor `vms` set → `ValueError`

### `load_experiment` parsing
- TOML with `vm = "x"` → `step.vms == ("x",)` (backward compat)
- TOML with `vms = ["a", "b"]` → `step.vms == ("a", "b")`
- TOML with both → `ValueError`
- TOML with neither → `ValueError`

### Fan-out (`tests/test_cli.py`)
- Mock `_run_experiment_step_on_vm` to record calls; assert all VMs in `step.vms` were called
- All VMs succeed → no failure counted
- One VM fails → `failed_steps` incremented; other VMs still ran (complete-then-report)

### Parallel batches (`tests/test_cli.py`)
- Mock `_run_experiment_step` with `time.sleep(0.05)`; assert wall time for 3-step batch < 0.15s (proves concurrency)
- Assert step after batch waits for batch to finish (ordering)
- Single `parallel=True` step with no neighbors → runs sequentially without error

### `continue_on_failure` integration
- Batch with one failure + `continue_on_failure = true` → experiment completes
- Batch with one failure, no flag → experiment aborts after batch completes

## What's out of scope (v0.19)

- Progress reporting for in-flight parallel tasks
- Per-step timeout
- Dynamic VM discovery (expanding `vms` from a tag or group)
- SSH-based remote executor (Phase 6 item)
- Run record schema changes (parallel steps are recorded as individual entries)
